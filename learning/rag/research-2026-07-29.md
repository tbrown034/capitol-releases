# Pre-build research synthesis — July 29, 2026

Three parallel research passes (chunking/embeddings, pgvector-on-Neon, eval/citation-grounding) run before implementation. Full reports appended below. This page records what we adopted, what we rejected, and why.

## Design decisions adopted from research

**1. Chunking: paragraph-packed ~800 tokens, hard cap 1,000, zero overlap.**
Jan 2026 systematic evidence: overlap adds cost, no benefit; structure-aware chunking matches semantic chunking below ~5k-token contexts. Our corpus (median ~650 tokens/release) means about half of releases stay whole. Expected ~145k passages from ~103k records.

**2. Metadata header prepended to embedded text.** Member name, party-state, date, title before the body. Measured retrieval win (prefix beats plain text), costs ~$0.07 across the corpus.

**3. Retrieved-context budget ~2,500 tokens.** Quality cliff above that. We send the top 3-4 passages, not ten.

**4. No vector index tonight — exact scan, member-scoped.** Every query filters to one member (100–2,500 passages); exact search gives perfect recall, zero tuning, and sidesteps two traps: HNSW post-filtering recall collapse, and the Neon HTTP driver's inability to persist `SET hnsw.iterative_scan` session state. A btree on `official_id` drives the scan. HNSW (m=16, ef_construction=64) is the documented path when cross-member search arrives.

**5. Column type `halfvec(1536)`.** Half the storage of `vector`, negligible recall loss on OpenAI embeddings. Neon ships pgvector 0.8.0+, which supports it. Embedding dims stay native 1536 (truncation would require re-normalization and costs recall on entity-heavy text).

**6. Hybrid = Reciprocal Rank Fusion in SQL.** Rank-based fusion avoids normalizing incomparable ts_rank and cosine scales. Reference pattern (Katz): per-leg LIMIT 40, k=50, final LIMIT 10. Adopted only if the golden-set numbers beat single-method retrieval — that decision stays evidence-gated.

**7. Citations: Claude API `search_result` content blocks, not prompt markers.**
The deleted prototype used prompt-based [n] markers plus regex validation. The API now has a GA, purpose-built path: retrieved passages go in as typed `search_result` blocks with citations enabled; the answer comes back as text blocks carrying server-generated citation objects (`cited_text`, `search_result_index`, block range). Validation becomes an equality assertion against data we sent — deterministic, no prompt-adherence failure mode. Constraint accepted: incompatible with JSON-schema structured outputs, so we parse content blocks. We pass each passage's paragraphs as separate text blocks inside its search_result, so citations land at paragraph granularity.

**8. Abstention: two-part prompt with exact refusal wording.** Closed-book instruction plus explicit permission to refuse ("reply exactly: Not in the record"). Golden set seeds 3 deliberately unanswerable questions; we score abstention correctness, not just retrieval.

**9. Eval at n=10: raw counts only.** recall@5, recall@10, MRR, passage-level ground truth. This is a smoke test against catastrophic breakage, not a benchmark — the honest framing is part of the interview story.

## Rejected or deferred (with reasons)

- **Contextual retrieval (Anthropic technique):** real measured gains (35-67% fewer retrieval failures) but ~145k Haiku calls of wall-clock and a second failure-prone write path. Deferred; top of the improvement list.
- **HNSW index:** premature at member-scoped query patterns. Deferred to cross-member search.
- **Semantic chunking, reranking, query rewriting:** baseline first, by prior decision; research confirms structure-aware chunking is competitive.
- **Batch embeddings API (50% off):** 24-hour completion window doesn't fit tonight; savings would be ~$1.
- **Narrow separate embedding table / STORAGE PLAIN:** flagged TOAST optimization, unverified for our row shape. Single table tonight; measure query latency in the retrieval block and split only if slow.

## Operational facts for tonight

- Backfill wall clock depends on OpenAI rate tier: ~17 min (Tier 2+) vs ~80 min (Tier 1). Check tier first; start backfill early; order senate-first so demo members embed first.

## Report 1: chunking + embeddings (research-chunking)

**Bottom line:** paragraph-pack to ~800-token chunks, no overlap, prepend title + date + member name, embed at native 1536 dims. Total cost about $2 and 20-80 minutes of wall clock. Skip contextual retrieval tonight.

### 1. Chunk size and method

The strongest current evidence is a January 2026 systematic study (Natural Questions, SPLADE retrieval, Mistral-8B) that varied method, size, overlap, and context length. Four findings apply directly:

- **Overlap provides no measurable benefit** and raises indexing cost. This contradicts the 10-20% overlap rule everyone learned in 2023.
- **Sentence/paragraph chunking matches semantic chunking** up to ~5k-token contexts, at a fraction of the cost. Semantic chunking is not worth building tonight.
- A **"context cliff" near 2,500 tokens** degrades answer quality — that caps total retrieved context, not per chunk.
- Optimal context depends on the goal: semantic quality peaks at small contexts, exact match at larger ones.

**Applied to your distribution** (median 650, p90 1,600, p99 3,500): paragraph-aware packer, 800-token target, 1,000-token hard cap. Roughly half your releases become a single chunk — do not split a document that already fits. Expect ~145k chunks from 97k releases. Overlap 0; if you want insurance, 50 tokens max.

Practitioner consensus still centers on 256-512 tokens, but that is tuned for long PDFs. Your documents are already chunk-sized, so the larger target keeps quotes intact with their attribution.

### 2. Prepend metadata: yes

A January 2026 paper comparing metadata strategies (prefix, suffix, dual-encoder fusion, query reformulation) found **prefixing and unified embeddings consistently beat plain-text baselines**. Mechanism: higher intra-document cohesion, less inter-document confusion. Field ablations showed entity and date fields carry strong disambiguating signal; section titles help less.

Format each chunk's embedded text as a short header: member name, party-state, date, title, then the chunk body. Costs ~25 tokens per chunk, about $0.07 across the corpus.

**Contextual retrieval: skip it.** Anthropic reports real gains — 35% fewer failed retrievals from contextual embeddings alone, 49% with contextual BM25, 67% with a reranker — at $1.02 per million document tokens with prompt caching. For 78M corpus tokens that is ~$80 and ~145k Haiku calls. The dollars are fine; the wall clock and a second failure-prone write path are not, for one night. Cheap metadata prefixing captures a meaningful share of the same benefit.

### 3. text-embedding-3-small specs

$0.02 per 1M tokens. Max 8,192 tokens per input, 1536 native dimensions, MTEB 62.26. The `dimensions` parameter truncates via Matryoshka down to 256 — **you must L2-renormalize after truncating.**

Per-request limits: **2,048 array inputs and 300,000 tokens summed across all inputs.** At 800-token chunks the token cap binds first, so batch ~250 chunks per request (~580 requests total).

Rate limits: Tier 1 is 500 RPM / 1M TPM; Tier 2 is 5,000 RPM / 5M TPM. Your ~82M total embed tokens means **~80 minutes at Tier 1, ~17 minutes at Tier 2** — check your tier before you start. Batch API offers 50% off but a 24-hour window; not worth it tonight.

Stay at 1536 dims. Truncating to 768 halves storage (~890MB down to ~445MB for 145k vectors) but costs recall on entity-heavy text.

### 4. What a 2023-2024 RAG engineer gets wrong

1. **Overlap is now considered dead weight**, not a default.
2. **Semantic chunking is no longer the aspirational upgrade** — structure-aware splitting matches it below ~5k tokens.
3. **Hybrid dense + lexical is table stakes.** Pure dense retrieval reliably misses exact lexical signals — bill numbers, member names, agency acronyms. You already have a tsvector column; use it, and fuse with reciprocal rank fusion.
4. **More retrieved context is not better** — the 2,500-token cliff means retrieve fewer, better chunks.

### Flagged as unverified

- No direct evidence found for a political/news-specific weakness in text-embedding-3-small. The named-entity limitation is a general property of subword text encoders, which is exactly why point 3 matters.
- The metadata paper's direction is confirmed from the abstract; per-field gain magnitudes not extracted.
- pgvector halfvec noted but Neon version verified in Report 2.

## Report 2: pgvector on Neon (research-pgvector)

**Bottom line: skip the vector index for now.** Queries are always scoped to one member with 100-2,500 passages. Exact search over that gives perfect recall, zero tuning, and no build step. Add HNSW only when cross-member search arrives.

### 1. Index choice

Exact (no vector index) for per-member queries. Put a plain btree on `official_id` so the filter drives the scan. 2,500 x 1536-dim cosine distances is roughly single-digit milliseconds of CPU; the cost is I/O to fetch the vectors, not the math. pgvector's own docs say the default is exact search with perfect recall, and that table scans are often faster than index use at small row counts.

If corpus-wide search is needed later, use HNSW, not IVFFlat. HNSW is the 2026 default — better recall, buildable on an empty table, no rebuild-as-data-grows requirement. Parameters: `m=16`, `ef_construction=64` (defaults, still the recommended production values), `hnsw.ef_search` 40 baseline / 100 for recall. For 400k rows expect single-digit minutes of build on a scaled-up Neon compute with adequate `maintenance_work_mem`.

### 2. Filtered search — the strongest argument for exact

Post-filtering recall collapse is real and severe. With `ef_search=40` and a filter matching ~0.6% of rows, an HNSW scan returns almost nothing relevant. pgvector 0.8's `hnsw.iterative_scan = strict_order` fixes it (capped by `hnsw.max_scan_tuples`, default 20,000).

**Stack-specific catch:** the `@neondatabase/serverless` HTTP driver has no session state, so `SET hnsw.iterative_scan` / `SET hnsw.ef_search` do not persist between queries. Fixes would be `sql.transaction` with `SET LOCAL` or the WebSocket Pool. Exact search needs neither. Per-member partial indexes would work but mean ~540 indexes.

### 3. Column type: `halfvec(1536)`

Storage `2*dims+8` = 3,080 bytes vs 6,152 for `vector` — exactly half, negligible recall loss on OpenAI embeddings. Neon supports pgvector **0.8.0 on PG14-17, 0.8.1 on PG18**, so halfvec and iterative scans are available. `CREATE EXTENSION IF NOT EXISTS vector;` per database.

**Trap worth testing:** vector columns default to TOAST EXTERNAL storage — scanning 2,500 vectors means 2,500 out-of-line fetches. A narrow table (`id, official_id, embedding`) and/or `SET STORAGE PLAIN` avoids it; halfvec at 3,080 bytes fits inline in an 8KB page. [NEEDS VERIFICATION for our row shape — measure before committing.]

### 4. Hybrid search: RRF, not weighted sums

RRF uses only rank position, avoiding normalization of incompatible `ts_rank_cd` and cosine scales. Katz's pattern is the reference: two subqueries each LIMIT 40, UNION ALL, `sum(1.0/(rank+k))` grouped by id, k=50, final LIMIT 10. Per-leg limits must exceed the final limit. One reported result: 62% precision vector-only → 84% with RRF. Caveat: not rigorously benchmarked against ground truth.

### 5. Neon build-time guidance

Scale compute up during backfill, down after. `maintenance_work_mem` ≤ 50-60% of compute RAM. `max_parallel_maintenance_workers` = CU count. Build indexes after loading data. `work_mem` 16-64MB to avoid OOM under concurrency.

## Report 3: eval + citation grounding (research-eval)

**Headline: don't build `[n]` markers + regex validation. Use `search_result` content blocks.** GA on the Claude API (also Bedrock, Vertex), no beta header, all active models except Haiku 3.

### 1. Citation grounding

Pass each retrieved chunk as `{type: "search_result", source, title, content: [{type: "text", text}], citations: {enabled: true}}` — in a user message (our case) or inside a tool_result. Claude splits the answer into text blocks; grounded blocks carry a `citations[]` array of `search_result_location` objects: `cited_text`, `source`, `title`, `search_result_index`, `start_block_index`, `end_block_index`.

Why it beats prompt markers: `cited_text` is server-generated and not billed as output tokens; `search_result_index` maps deterministically back to the block sent; no prompt-adherence failure mode to regex around.

Constraints: the text block is the minimal citable unit (split releases into paragraph-level blocks or citations point at the whole document); `search_result` is rejected in assistant messages; incompatible with structured outputs (`output_config.format` → 400) — parse content blocks.

### 2. Retrieval eval at n=10

recall@k primary, MRR secondary; precision@k mostly irrelevant here. Report k=5 and k=10. Label at **passage level, not document level**. At n=10 report raw counts ("8/10 gold passage in top 5"), never percentages — smoke test, not benchmark. Real golden sets run ~100 questions.

### 3. Abstention

Two-part: closed-book instruction ("answer only from the provided search results") plus explicit permission with exact output wording ("If the record does not contain the answer, reply exactly: Not in the record."). The permission removes false-confidence pressure. Measure by seeding 2-3 deliberately unanswerable questions; track refusal and hallucination rates. A controlled 30-query study moved refusal 0.767 → 0.828 and hallucination 0.128 → 0.083.

### 5. Quote verification

Normalized exact-substring matching is a recognized deterministic guardrail (normalize whitespace/quote chars, require exact contiguous substring, else drop). Documented limit: proves the quote is in the source, not that it supports the claim. With `search_result` citations, assert `cited_text == "".join(blocks[start:end])` — equality against our own data, not a search. Fuzzy matching (~80% token overlap) only as fallback for prompt-based approaches.
